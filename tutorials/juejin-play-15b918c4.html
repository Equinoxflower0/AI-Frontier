🎯 为什么值得玩

很多团队在构建 AI Agent 时，习惯把所有工具（API、函数）的定义一股脑塞进系统提示词。工具少时没问题，一旦超过 20 个，上下文成本飙升，模型还容易选错工具或漏选依赖工具。本文基于掘金实战教程，实现一套轻量级工具检索与补全机制：先用 BM25 根据用户 query 召回相关工具，再根据工具间的依赖关系自动补全必要的前置工具，最后按风险等级过滤掉高危操作，只把最精简、最安全的工具集交给 Agent。

📝 一步步教你做

1

第1步：定义工具元数据与依赖关系

为每个工具准备结构化描述：名称、功能描述、参数、依赖的其他工具列表、风险等级（low/medium/high）。例如“发送邮件”依赖“查询联系人”，“删除数据库”风险等级为 high。把这些元数据存成 JSON 或 Python 字典列表，作为后续检索和过滤的基础。
💡 小贴士：描述字段尽量用自然语言写清楚使用场景，BM25 靠关键词匹配，描述越贴近用户问法召回越准。
2

第2步：用 BM25 根据用户 query 召回候选工具

将每个工具的描述文本拼接成文档，用 rank_bm25 建立索引。用户输入 query 后，对 query 分词并计算 BM25 得分，取 Top-K（如 K=5）作为候选工具。注意对中文先做简单分词（可用 jieba），英文直接空格切分。
💡 小贴士：K 不要设太大，5~8 足够；如果召回结果太少，可以适当降低 BM25 阈值或增加同义词扩展。
3

第3步：依赖补全——自动加入前置工具

遍历候选工具，检查每个工具的依赖列表。如果某个依赖工具不在候选集中，就把它加入。递归检查直到没有新的依赖被加入。这样确保 Agent 拿到的是“可执行闭环”的工具集，而不是孤立的工具。
💡 小贴士：依赖关系建议只保留直接依赖，避免循环依赖；可以用 visited 集合防止死循环。
4

第4步：风险过滤——剔除高危工具

根据工具的风险等级过滤：如果候选集中包含 high 风险工具，可以选择直接移除，或者替换为低风险的只读版本（如“查询”代替“删除”）。也可以设置策略：只有用户明确授权时才保留 high 风险工具。
💡 小贴士：风险等级不要写死，建议放在配置文件中，方便不同环境（开发/生产）切换策略。
5

第5步：组装精简 Prompt 并调用 Agent

把最终工具集（通常 3~8 个）格式化成工具定义文本，插入系统提示词，再拼接用户 query 调用 LLM。观察模型是否选择了正确的工具链。可以打印每次召回和补全的结果，便于调试。
💡 小贴士：在 Prompt 中明确告诉模型“你只能使用以下工具”，并给出工具调用格式示例，能进一步降低误选。

✨ 完成后你会得到

Agent 每次只收到 3~8 个相关且安全的工具定义，上下文长度显著下降，工具选择准确率提升，高危操作被自动拦截。你可以在日志中看到：用户 query → BM25 召回 Top5 → 依赖补全后 6 个 → 风险过滤后 5 个 → 最终 Prompt 长度减少 70% 以上。

❓ 常见问题

BM25 对中文效果不好怎么办？ ▼
先对工具描述和 query 做分词（推荐 jieba），再建索引；也可以加入同义词词典扩展 query，或者换用轻量向量检索（如 sentence-transformers）做混合召回。
依赖补全会不会把工具集撑得太大？ ▼
通常不会。依赖链一般很短（1~2 层），补全后工具数仍在个位数。如果依赖过多，说明工具粒度太细，建议合并工具或重新设计接口。
风险过滤会不会误删必要工具？ ▼
可以分级处理：high 风险工具默认移除，但保留一个“申请授权”的占位提示；或者只移除写操作，保留读操作。策略应结合业务场景调整。
没有 OpenAI API 可以用吗？ ▼
可以。任何支持 function calling 的模型都行，比如 Claude、通义千问、DeepSeek 等。只需替换调用代码，工具检索与补全逻辑完全复用。
这套方法适合多少工具规模？ ▼
20~200 个工具效果最明显。少于 10 个时收益不大；超过 200 个建议引入向量检索或分层工具目录。

🚀 进阶玩法

  • 🔹 变体1：混合检索——BM25 召回后，再用轻量向量模型（如 text2vec）对 Top20 重排序，提升语义匹配准确率。
  • 🔹 变体2：动态风险策略——根据用户身份或会话上下文动态调整风险阈值，例如管理员会话保留 high 风险工具，普通用户则过滤。
  • 🔹 变体3：工具分组路由——先让 LLM 判断 query 属于哪个业务域（如“邮件”“数据库”“文件”），再只在对应分组内做 BM25 检索，进一步缩小候选集。

💡 一句话总结

用 BM25 精准召回、依赖补全保闭环、风险过滤守安全，三招把 Agent 的工具集从“全量塞入”变成“按需精简”，上下文更省、选择更准、运行更安全。
