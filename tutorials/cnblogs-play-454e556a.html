在前后端分离和微服务架构中，JWT 是无状态认证的主流方案，但很多教程只讲签发不讲刷新，导致令牌过期后用户体验断裂。本文基于博客园的一篇动手示例，带你从创建项目开始，逐步实现注册、登录、JWT 验证、Refresh Token 轮换，并补上一个可操作的中文页面，最终通过动态图看到完整流程。适合有一定 C# 基础、想快速掌握认证授权的开发者。

📝 一步步教你做

1

第1步：创建项目并安装 JWT 相关包

打开终端执行 dotnet new webapi -n JwtAuthDemo 创建项目，进入目录后安装 Microsoft.AspNetCore.Authentication.JwtBearer 和 System.IdentityModel.Tokens.Jwt 包。在 Program.cs 中注册认证服务，配置 JWT 的 Issuer、Audience 和对称密钥。
💡 小贴士：密钥不要硬编码在代码里，开发阶段可用 appsettings.Development.json，生产环境务必用环境变量或密钥管理服务。
2

第2步：实现用户注册与登录接口

创建 User 实体和 AppDbContext，用 EF Core 的 InMemory 或 SQLite 快速建库。编写 /api/auth/register 接口接收用户名密码，用 BCrypt 或 PBKDF2 哈希后存库；编写 /api/auth/login 接口校验密码，成功后签发 Access Token（短期，如 15 分钟）和 Refresh Token（长期，如 7 天），并把 Refresh Token 存入数据库。
💡 小贴士：密码哈希不要用 MD5/SHA1，推荐 BCrypt.Net-Next 包，一行代码搞定加盐哈希。
3

第3步：配置 JWT 验证中间件并保护接口

在 Program.cs 中调用 AddAuthentication(JwtBearerDefaults.AuthenticationScheme).AddJwtBearer(...) 配置 TokenValidationParameters，包括 ValidateIssuer、ValidateAudience、ValidateLifetime 和 IssuerSigningKey。然后调用 app.UseAuthentication() 和 app.UseAuthorization()。给需要保护的控制器或 Action 加上 [Authorize] 特性，测试未带 Token 时返回 401。
💡 小贴士：调试时如果一直 401，先检查 Token 是否过期、密钥长度是否满足 HS256 要求（至少 32 字节）。
4

第4步：实现 Refresh Token 轮换接口

新增 /api/auth/refresh 接口，接收过期的 Access Token 和 Refresh Token。校验 Refresh Token 是否存在于数据库且未过期、未撤销，若有效则生成新的 Access Token 和新的 Refresh Token，并将旧的 Refresh Token 标记为已撤销（轮换）。返回新令牌对给客户端。
💡 小贴士：轮换时务必把旧 Refresh Token 作废，防止重放攻击；可以给 Refresh Token 加一个 FamilyId 来检测令牌盗用。
5

第5步：补一个中文操作页面并联调

在 wwwroot 下创建一个简单的 HTML 页面，用 fetch 调用注册、登录、获取天气（受保护接口）和刷新令牌接口。登录成功后把 Token 存到 localStorage，请求时带上 Authorization: Bearer <token>。当接口返回 401 时自动调用刷新接口，刷新成功后重试原请求。
💡 小贴士：前端存储 Token 有 XSS 风险，生产环境建议用 HttpOnly Cookie 存 Refresh Token，Access Token 放内存。

❓ 常见问题

Access Token 和 Refresh Token 的有效期设多长合适？ ▼
Access Token 建议 5-15 分钟，Refresh Token 建议 7-30 天，并根据业务安全等级调整。
Refresh Token 存数据库还是 Redis？ ▼
单机或小规模用数据库即可；高并发场景推荐 Redis，并设置过期时间自动清理。
为什么刷新后旧 Token 还能用？ ▼
说明没有做轮换撤销，需要在刷新接口里把旧 Refresh Token 标记为已使用或删除。
前端如何判断 Token 过期？ ▼
可以解析 JWT 的 exp 字段，或直接等接口返回 401 再触发刷新逻辑。
MCP 鉴权是什么？ ▼
原文提到的 MCP 鉴权是扩展场景，核心仍是基于 JWT 的 Bearer 认证，按同样方式加 [Authorize] 即可。

🚀 进阶玩法

  • 🔹 变体1：把 Refresh Token 存到 HttpOnly Cookie 中，前端不接触 Refresh Token，降低 XSS 风险。
  • 🔹 变体2：引入 Redis 做分布式令牌存储，支持多实例部署和主动踢人下线。
  • 🔹 变体3：增加角色/权限声明（Role/Claim），实现基于策略的细粒度授权。
