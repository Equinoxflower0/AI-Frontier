🎯 为什么值得玩

传统 AI 编程助手只能在你指定的单个终端里跑命令，遇到需要并行开多个窗格、分别监控不同服务、或根据输出动态切换目录的场景就捉襟见肘。Zerg 是一个 coding agent harness，它把终端窗格当作可编程资源，智能体可以自主创建、切换、读写多个终端 pane，从而完成「启动前端 → 开另一个窗格跑后端 → 再开一个窗格看日志」这类真实开发工作流。这个玩法适合本地开发调试、多服务联调、以及需要 AI 自主排错并验证结果的场景。

📝 一步步教你做

1

第1步：安装并初始化 Zerg

从 Product Hunt 页面进入 Zerg 官网，按文档用 npm 全局安装（或 npx 直接运行）。安装完成后在项目根目录执行初始化命令，填入你的 LLM API Key，并确认 Zerg 能检测到当前终端支持多窗格（tmux 或 iTerm2）。
💡 小贴士：如果检测不到窗格能力，先在 tmux 会话里启动 Zerg，成功率最高。
2

第2步：用自然语言描述多窗格任务

在 Zerg 的交互界面输入类似「打开三个终端窗格：第一个运行 npm run dev 启动前端，第二个运行 node server.js 启动后端，第三个 tail -f logs/app.log 监控日志，等前端编译完成后告诉我访问地址」的指令。Zerg 会解析意图并规划窗格分配。
💡 小贴士：把每个窗格要跑的命令和预期结果写清楚，智能体分配窗格会更准确。
3

第3步：观察智能体自主开窗与执行

Zerg 会依次创建终端 pane、写入命令、读取输出。你可以在界面上看到每个窗格的实时状态：哪个在编译、哪个已就绪、哪个报错。如果某个窗格命令失败，Zerg 会自动读取错误输出并尝试修复（如换端口、装依赖）。
💡 小贴士：不要手动去抢窗格操作，让智能体自己完成闭环，否则容易打断它的状态跟踪。
4

第4步：根据输出做二次指令

当 Zerg 汇报「前端已就绪在 3000 端口，后端在 4000 端口」后，你可以继续下指令，比如「在第四个窗格用 curl 测试 /api/health 接口，把结果贴出来」或「如果日志里出现 ERROR 就自动重启后端」。Zerg 会新开窗格或复用现有窗格执行。
💡 小贴士：用「如果…就…」的条件句式，能触发 Zerg 的自主监控与响应能力。
5

第5步：收尾与清理

任务完成后，让 Zerg「关闭所有它自己开的窗格并汇总本次执行日志」。Zerg 会逐个退出 pane 并生成一份操作摘要，方便你复盘哪些命令被自动执行过。
💡 小贴士：保留摘要日志，下次可以让 Zerg 参考历史记录跳过重复的环境检查。

✨ 完成后你会得到

Zerg 自主创建 3-4 个终端窗格，分别运行前端、后端、日志监控和接口测试，并在主界面汇总每个窗格的状态与关键输出。你无需手动切换窗格，就能看到前后端联调成功、健康检查返回 200、日志无 ERROR。

❓ 常见问题

Zerg 支持 Windows 吗？ ▼
官方主要面向 macOS/Linux 的 tmux 与 iTerm2 环境；Windows 建议在 WSL2 里用 tmux 运行，或使用 Windows Terminal 的多窗格配合兼容层。
智能体开的窗格会和我手动开的冲突吗？ ▼
Zerg 会为自己创建的 pane 打标记并独立管理，一般不会动你已有的窗格；但建议在专用 tmux 会话里运行以避免误操作。
需要多强的模型？ ▼
建议使用支持工具调用（function calling）的较强模型，如 GPT-4o 或 Claude 3.5 Sonnet，弱模型容易在窗格状态跟踪上出错。
命令执行安全吗？ ▼
Zerg 默认会在执行破坏性命令前请求确认；你可以在配置里开启「只读模式」先观察它的规划，确认无误再放开执行。
可以接入 CI 或远程服务器吗？ ▼
可以，只要目标环境有 tmux，Zerg 能通过 SSH 在远程会话里开窗格；CI 场景建议用非交互模式并限制可用命令白名单。

🚀 进阶玩法

  • 🔹 变体1：多服务监控——让 Zerg 开 N 个窗格分别 tail 不同微服务日志，并设置关键词告警，一旦出现 ERROR 自动在另一个窗格执行重启脚本。
  • 🔹 变体2：AI 自主排错——给 Zerg 一个失败测试用例，让它自己开窗格跑测试、读报错、改代码、再跑测试，形成闭环直到通过。
  • 🔹 变体3：远程开发机编排——通过 SSH 连到远程服务器，让 Zerg 在远程 tmux 里开窗格部署服务、跑迁移、看状态，本地只做指令下发。

把终端窗格变成 AI 可编程的资源，让智能体自己开窗、跑命令、读输出、做决策——这就是 Zerg 的核心玩法。
