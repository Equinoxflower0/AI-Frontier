🎯 为什么值得玩

在真实运维场景中，排查一个 API 超时往往需要同时看日志、指标、链路追踪、数据库慢查询等多个数据源。单个 Agent 很难独立完成，而让多个 Agent 依次传递上下文又容易丢失关键信息。黑板架构借鉴经典 AI 设计模式：所有 Agent 共享一块「黑板」写入和读取发现，围绕同一问题持续协作。本玩法适合复杂故障排查、多源数据分析、跨系统根因定位等场景，难度中等偏上，但一旦跑通可复用到很多协作型任务。

📝 一步步教你做

1

第1步：定义黑板数据结构与协作协议

在 Redis 中设计一个 Hash 结构作为黑板，键为 `blackboard:{incident_id}`，字段包括 `problem`（问题描述）、`findings`（各 Agent 写入的发现列表）、`hypotheses`（待验证假设）、`conclusion`（当前结论）。同时约定每个 Agent 写入格式：`{agent, timestamp, observation, evidence, confidence}`。这样所有 Agent 都能以统一格式读写，避免上下文丢失。
💡 小贴士：用 Redis List 存 findings 可以保留写入顺序，方便回溯推理链；给每个 incident 设置 TTL 防止黑板无限增长。
2

第2步：搭建三个数据源 Agent

在 Dify 中分别创建日志 Agent、指标 Agent、链路 Agent。每个 Agent 配置对应的查询工具：日志 Agent 接 Elasticsearch 查询接口，指标 Agent 接 Prometheus HTTP API，链路 Agent 接 Jaeger API。每个 Agent 的提示词模板统一为：「你是{角色}，请针对问题{problem}查询数据，将发现按约定格式写入黑板，并读取黑板中其他 Agent 的发现作为参考。」
💡 小贴士：提示词里明确要求 Agent 先读黑板再查询，能显著减少重复查询和无效发现。
3

第3步：编排协作循环与仲裁 Agent

在 Dify 工作流中设置一个循环节点：依次调用三个数据源 Agent，每轮结束后由仲裁 Agent 读取黑板全部内容，判断是否已能定位根因。若不能，仲裁 Agent 生成新的假设写入 `hypotheses`，并指定下一轮各 Agent 的查询重点。循环最多执行 3-5 轮，避免无限循环。
💡 小贴士：仲裁 Agent 的提示词要强调「基于证据判断」，并要求输出结构化的 `{status: continue|done, next_focus: ...}`，便于工作流分支。
4

第4步：注入初始问题并触发排查

向黑板写入初始 `problem`：「报表导出 API 在每日 10:00-11:00 出现 P99 超时超过 30s，影响约 5% 请求。」然后触发工作流。各 Agent 第一轮会分别查询该时段日志错误、接口耗时指标、慢链路 span，并将发现写入黑板。
💡 小贴士：初始问题描述越具体（时间窗口、影响面、指标阈值），Agent 查询越聚焦，排查效率越高。
5

第5步：观察协作过程并人工干预

在 Dify 运行日志中实时查看每轮黑板内容变化，重点关注 `findings` 是否出现交叉印证（如日志 Agent 发现慢 SQL，链路 Agent 发现 DB span 耗时占比高）。若发现某 Agent 跑偏，可手动向黑板写入提示或调整其查询范围，再继续循环。
💡 小贴士：把黑板内容定期导出为 Markdown 复盘文档，既是故障报告也是 Agent 协作的调试素材。
6

第6步：输出根因报告与沉淀

当仲裁 Agent 判定 `status: done` 时，让它基于黑板全部内容生成根因报告，包含：问题现象、各 Agent 关键发现、证据链、根因结论、修复建议。将报告和黑板快照存入知识库，供后续类似问题检索复用。
💡 小贴士：要求仲裁 Agent 在报告中标注每条结论对应的黑板 finding 编号，保证可追溯。

✨ 完成后你会得到

工作流运行 2-4 轮后，黑板中汇聚日志、指标、链路三方的交叉证据，仲裁 Agent 输出结构化根因报告（例如「慢 SQL 导致 DB 连接池耗尽，进而引发导出 API 超时」），并附带完整证据链和修复建议。整个过程可在 Dify 运行日志中回放，黑板快照可导出复盘。

❓ 常见问题

黑板用 Redis 还是用文件/数据库？ ▼
小规模实验用 JSON 文件或 SQLite 即可；多 Agent 并发读写建议用 Redis，支持原子操作和 TTL，部署也简单。
Agent 之间会不会互相污染错误发现？ ▼
会。所以每条 finding 必须带 confidence 和 evidence 字段，仲裁 Agent 要基于证据而非投票做判断，必要时人工干预剔除低质量发现。
循环几轮比较合适？ ▼
一般 3-5 轮足够。超过 5 轮仍无结论，说明问题描述或数据源覆盖不足，应人工介入而不是继续烧 token。
没有 Dify 能用别的工具吗？ ▼
可以。FastGPT、Coze、n8n 甚至自己用 Python + LangChain 都能实现，核心是「共享存储 + 循环编排 + 仲裁判断」三要素。
这个玩法只能用于排查 API 超时吗？ ▼
不是。任何需要多源数据交叉验证的复杂问题都适用，如安全事件分析、用户流失归因、供应链异常定位等。

🚀 进阶玩法

  • 🔹 变体1：把黑板换成向量数据库，让每个 Agent 写入发现时自动生成 embedding，仲裁 Agent 用语义检索找相关发现，适合发现数量大、需要模糊关联的场景。
  • 🔹 变体2：引入「红队 Agent」专门挑战其他 Agent 的结论，在黑板中写入反例和质疑，提升根因判断的严谨性，适合高 stakes 的生产故障复盘。
  • 🔹 变体3：将黑板架构用于产品需求评审，让市场、技术、设计三个 Agent 围绕同一需求文档持续写入风险和方案，仲裁 Agent 汇总评审结论。

💡 一句话总结

黑板架构的精髓是：用一块共享存储让多个 Agent 围绕同一问题持续读写发现，配合仲裁 Agent 控制循环，把「各自为战」变成「交叉印证」的协作排查。
