🎯 为什么值得玩

很多 AI 应用卡在「一条链跑到底」：中间出错只能重来，分支逻辑写死在代码里，多步工具调用难以追踪。LangGraph 用「状态 + 节点 + 边」的图结构解决这些问题——状态用 TypedDict/Pydantic 定义，Reducer 负责合并并发写入，条件边控制分支与循环，Checkpointer 让流程可断点恢复。它适合需要多步推理、工具调用、人工审核或失败重试的复杂 Agent 场景。

📝 一步步教你做

1

第1步：安装依赖并定义状态结构

先 pip install langgraph langchain langchain-openai。然后用 TypedDict 定义图的状态，例如 messages 列表和 next_step 字符串；如果需要对并发写入做合并，给字段加上 Annotated[list, add_messages] 这样的 Reducer。简单场景用 TypedDict 即可，需要校验和默认值时改用 Pydantic BaseModel。
💡 小贴士：状态字段宁少勿多，只放节点间真正需要传递的数据，避免图变成全局变量垃圾场。
2

第2步：编写节点函数并注册到 StateGraph

每个节点就是一个普通函数，入参是 state，返回要更新的字段字典。用 StateGraph(State) 创建图，add_node("llm", llm_node) 逐个注册节点。节点内可以调用模型、执行工具或做纯逻辑判断。最后用 set_entry_point 指定入口节点。
💡 小贴士：节点函数保持单一职责，一个节点只做一件事，调试时更容易定位问题。
3

第3步：用条件边控制分支与循环

用 add_conditional_edges 挂上路由函数，根据 state 里的字段返回下一个节点名。例如判断是否需要调用工具：需要则走向 tools 节点，不需要则走向 END。循环终止条件也在这里判断，比如工具调用次数超过 3 次就强制结束，防止死循环。
💡 小贴士：路由函数只做判断不做副作用，返回字符串即可，方便单元测试。
4

第4步：加入 Checkpointer 实现可恢复

编译图时传入 checkpointer=MemorySaver()（生产环境换 SqliteSaver 或 PostgresSaver），并在 invoke 时带上 config={"configurable": {"thread_id": "user-1"}}。这样每一步状态都会落盘，中断后可以用同一 thread_id 从上次断点继续跑。
💡 小贴士：thread_id 按用户或会话维度生成，恢复时传同一个值才能接上历史状态。
5

第5步：运行、可视化并调试

调用 graph.invoke({"messages": [("user", "帮我查天气并决定穿什么")]}) 跑通全流程。用 graph.get_graph().draw_mermaid_png() 导出流程图检查分支是否符合预期。观察每步输出，确认 Fan-in 汇聚和循环终止都按设计执行。
💡 小贴士：先跑最小用例再逐步加分支，图越复杂越要小步验证。

❓ 常见问题

TypedDict 和 Pydantic 状态到底怎么选？ ▼
需要运行时校验、默认值或复杂嵌套时用 Pydantic；追求轻量和简单结构时用 TypedDict。两者都支持 Annotated Reducer。
多个节点同时写同一个字段会怎样？ ▼
没有 Reducer 会报错冲突；给字段加 Annotated[list, add_messages] 或自定义合并函数即可安全合并并发写入。
循环停不下来怎么办？ ▼
在条件边里加计数器字段，路由函数判断超过阈值就返回 END；同时给 LLM 调用设置超时。
MemorySaver 重启后状态还在吗？ ▼
不在，MemorySaver 只存内存。生产环境换 SqliteSaver 或 PostgresSaver 持久化。
能接入本地模型吗？ ▼
可以，把 ChatOpenAI 换成 ChatOllama 或任何 LangChain 兼容的模型封装即可，图结构不变。

🚀 进阶玩法

  • 🔹 变体1：人工审核节点——在工具调用前插入 interrupt，等待人工确认后再继续，适合高风险操作。
  • 🔹 变体2：多 Agent 协作图——把每个 Agent 做成子图，用父图编排路由，实现研究员+写作员+审核员的分工。
  • 🔹 变体3：RAG 检索工作流——检索节点与生成节点组成循环，根据答案置信度决定是否重新检索。
