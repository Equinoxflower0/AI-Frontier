🎯 为什么值得玩

很多团队在搭建多 Agent 系统时，习惯为每个 Agent 配不同模型，导致成本高、维护乱。这篇玩法来自博客园 AI 教程，核心思路是：只保留 deepseek/deepseek-flash 一个模型，把 Agent 之间的差异全部交给 thinking tier 表达。11 月的改动把思考档从三档扩到四档，并重排了 Agent 档位，同时强调“Agent 级权限不得放宽全局默认”。这套方案适合想用单模型低成本构建多角色 Agent 的开发者。

📝 一步步教你做

1

第1步：统一模型入口，锁定 deepseek-flash

在项目配置中只保留一个模型标识 deepseek/deepseek-flash，删除其他模型分支。所有 Agent 的模型字段都指向这个常量，避免后续误配。用环境变量 DEEPSEEK_API_KEY 注入密钥，base_url 指向 https://api.deepseek.com。这样后续所有差异都只能通过思考档位表达，从架构上杜绝“换模型解决一切”的惯性。
💡 小贴士：把模型名写成常量 MODEL = "deepseek/deepseek-flash"，全局引用，改一处即可。
2

第2步：定义四档思考配置（默认档到 #max）

在代码中定义四档 thinking tier：default（默认档，低延迟）、high（高思考）、ultra（超高思考）、#max（最大思考，用于最复杂任务）。每档对应不同的 reasoning 参数或提示词前缀，例如 #max 档会在系统提示中追加“请进行多步深度推理并给出验证”。把四档封装成枚举或字典，方便 Agent 引用。注意档位越高，token 消耗和延迟越大，需要按任务复杂度分配。
💡 小贴士：先用 default 档跑通全流程，再逐档调高，避免一上来就 #max 导致成本失控。
3

第3步：重排 Agent 档位映射

为每个 Agent 角色指定一个思考档位：简单路由 Agent 用 default，分析类 Agent 用 high，规划类用 ultra，核心决策或复杂推理用 #max。把映射写成配置表（如 YAML 或 Python dict），Agent 初始化时读取。11 月改动强调重排档位，建议按“任务复杂度 × 错误代价”两个维度重新评估，而不是沿用旧三档的惯性分配。
💡 小贴士：给每个 Agent 加一行注释说明为什么选这个档，方便后续复盘调整。
4

第4步：落实权限约束——Agent 级不得放宽全局默认

在配置加载层加一条校验规则：Agent 级配置只能收紧权限，不能放宽全局默认。例如全局默认禁止文件写入，某个 Agent 不能通过配置开启写入。实现方式是在合并配置时做单向覆盖检查，发现 Agent 试图放宽就抛错或降级。这条规则能防止高思考档 Agent 因“更聪明”而被误授过高权限。
💡 小贴士：把校验写成单元测试，每次改配置自动跑，防止回归。
5

第5步：跑通一个最小 Agent 链并观测档位差异

构造一个两段式 Agent 链：第一个 Agent 用 default 档做意图分类，第二个 Agent 用 #max 档做复杂回答。用同一组输入分别跑四档，记录延迟、token 消耗和回答质量。观察 default 到 #max 的边际收益，判断哪些 Agent 值得升档。把观测结果回写到档位映射表，形成“配置—观测—调优”的闭环。
💡 小贴士：用简单脚本打印每档的 latency 和 completion_tokens，比凭感觉调档靠谱得多。

✨ 完成后你会得到

项目里只有一个模型 deepseek/deepseek-flash，所有 Agent 通过四档 thinking tier 区分行为；配置校验能阻止 Agent 级权限放宽；跑最小链时能看到 default 到 #max 的延迟与质量梯度，并据此完成档位调优。

❓ 常见问题

四档思考具体怎么在 API 里表达？ ▼
DeepSeek 的 reasoning 相关参数或提示词前缀均可表达档位，具体字段以官方文档为准；核心是把档位封装成统一配置，而不是散落在各 Agent 代码里。
为什么不让每个 Agent 用不同模型？ ▼
多模型会带来成本、版本、维护三重碎片化。单模型加思考档位能把差异收敛到一个维度，调优和回滚都更简单。
#max 档会不会太贵？ ▼
会。所以只给错误代价最高的核心决策 Agent 用 #max，其余按复杂度降档，并用观测数据验证边际收益。
权限不得放宽全局默认，具体怎么校验？ ▼
在配置合并时做单向覆盖检查：Agent 配置只能把权限从宽改窄，反向修改直接报错或降级。
这套方案适合什么规模的团队？ ▼
适合已有多个 Agent 角色、开始感到模型配置混乱的中小团队；单人小项目也可用，但收益在角色变多后更明显。

🚀 进阶玩法

  • 🔹 变体1：把四档映射成提示词模板库，每档对应一段系统提示前缀，不改 API 参数也能实现档位差异。
  • 🔹 变体2：加一个自动选档器，用小模型或规则先判断任务复杂度，再动态分配 default/high/ultra/#max。
  • 🔹 变体3：把档位配置外置为 YAML，配合 CI 做权限单向校验和档位回归测试，形成工程化流水线。

单模型是底座，四档思考是旋钮，权限单向约束是保险丝——三者合起来才是可工程化的 Agent 配置。
