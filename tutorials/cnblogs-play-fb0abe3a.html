很多人做 AI 应用还停留在「写个提示词问一句答一句」的阶段，但真正的 Agent 需要能拆解任务、检索知识、调用工具、循环纠错。博客园这篇《用五层技术栈搭建自主AI Agent》把提示词工程、RAG、Harness 工程、ReAct 循环、多智能体协作串成了一条完整链路。本教程把它拆成可动手的步骤，适合有一定 Python 基础、想从「调 API」进阶到「造系统」的开发者。跟着做完，你会得到一个能自主完成多步任务的 Agent 原型。

📝 一步步教你做

1

第1步：搭好环境并跑通最小 LLM 调用

先创建虚拟环境，执行 pip install llama-index llama-index-llms-openai llama-index-tools-tavily-research chromadb。然后在 Jupyter 里配置 OPENAI_API_KEY 环境变量，用 Settings.llm = OpenAI(model="gpt-4o-mini") 设置全局模型，发一句「你好」验证连通。这一步的目的是确认底座没问题，后面所有层都依赖它。
💡 小贴士：如果用的是国内兼容接口，记得同时设置 api_base，并把模型名换成对应名称，否则会报 404。
2

第2步：写好提示词层，把意图说清楚

提示词层是 Agent 的「大脑说明书」。用 ChatPromptTemplate 定义系统角色，明确写出：你是任务规划助手，输出必须是 JSON，包含 task 和 steps 两个字段。把用户原始需求套进模板，先让模型只做规划、不执行，观察它拆出的步骤是否合理。反复调 2-3 轮措辞，直到拆解稳定。
💡 小贴士：在提示词里加一句「如果信息不足，先列出需要澄清的问题」，能显著减少 Agent 瞎编。
3

第3步：接入 RAG 层，让 Agent 有外部知识

准备一份 PDF 或 Markdown 知识文档，用 SimpleDirectoryReader 读取，配合 VectorStoreIndex 建索引并持久化到 Chroma。把索引封装成 QueryEngineTool，描述写成「用于查询内部知识库」。这样 Agent 在规划时就能判断什么时候该查资料，而不是全靠模型记忆。
💡 小贴士：工具描述（description）写得越具体，Agent 选工具的准确率越高，别偷懒只写「查询工具」。
4

第4步：用 ReAct 循环把工具串起来

用 ReActAgent 或 FunctionAgent 把上一步的 RAG 工具和 Tavily 搜索工具一起注册进去。设置 max_iterations=10 防止死循环，然后丢一个多步任务，比如「查一下 LlamaIndex 最新版本，并对比我知识库里的旧版本差异」。观察日志里 Thought → Action → Observation 的循环过程，确认它真的在自主决策。
💡 小贴士：第一次跑建议把 verbose 打开，逐条看 Agent 的思考轨迹，出问题一眼就能定位是哪一层断了。
5

第5步：加 Harness 工程，让运行稳定可靠

Harness 层负责兜底：给每次工具调用加 try/except 和超时，失败时把错误信息回传给模型让它重试；用 memory 保存对话上下文；对最终输出做格式校验，不合格就触发一次自我修正。再包一层日志，记录每步耗时和 token 消耗。这一步做完，Agent 才从「玩具」变成「能交付」的系统。
💡 小贴士：给工具调用设 30 秒超时，并限制重试 2 次，能避免 Agent 卡死在某个坏接口上。
6

第6步：进阶到多智能体协作（可选）

如果任务复杂，可以用 AgentWorkflow 定义「规划者」和「执行者」两个角色：规划者负责拆任务，执行者负责调工具，二者通过共享上下文传递结果。跑一个「调研 + 写报告」的组合任务，观察两个 Agent 如何交接。这一步是五层栈的顶层，也是最能体现「数字员工」形态的地方。
💡 小贴士：多智能体容易互相甩锅，给每个角色写死职责边界和输出格式，协作会顺畅很多。

❓ 常见问题

没有 OpenAI Key 能玩吗？ ▼
可以，用 Ollama 跑本地模型（如 qwen2.5），把 Settings.llm 换成 Ollama 即可，但工具调用能力会弱一些，建议选支持 function calling 的模型。
ReAct 循环一直转不停怎么办？ ▼
设置 max_iterations 上限，并在提示词里要求「信息足够时立即输出 Final Answer」，同时检查工具描述是否让模型误以为还要继续查。
RAG 检索结果不相关怎么调？ ▼
先调 chunk_size 和 similarity_top_k，再考虑换 embedding 模型；也可以在 QueryEngineTool 的描述里限定适用范围，减少误触发。
五层必须全上吗？ ▼
不必。简单任务提示词 + 工具就够；RAG 和 Harness 按需加；多智能体只在任务确实需要分工时才上，否则是过度设计。
这套东西能上生产吗？ ▼
原型可以，生产还需要加鉴权、限流、可观测性和人工审核节点，Harness 层要补得更厚。

🚀 进阶玩法

  • 🔹 变体1：把搜索工具换成数据库查询工具，做一个能自主查业务数据的「分析助手」，适合运营和 BI 场景。
  • 🔹 变体2：用多智能体做「客服 + 工单」流水线，一个 Agent 分类问题，一个 Agent 查知识库回复，一个 Agent 决定是否转人工。
  • 🔹 变体3：把 Harness 层做成可配置的 YAML，把工具、超时、重试策略外置，快速复用到不同业务 Agent 上。

💡 一句话总结

五层技术栈的精髓不是堆技术，而是让每一层各司其职：提示词定意图、RAG 补知识、Harness 保稳定、ReAct 给自主、多智能体做分工，串起来才是一个能交付结果的数字员工。
