🎯 为什么值得玩

电梯维保是典型的工业级场景：既要秒级响应日常问答，又要在故障诊断时调用强模型做深度推理，同时必须满足特种设备安全法规的零事故要求。单一模型要么贵要么慢，双路由架构让简单问题走 Flash、复杂问题走 Pro，再配合混合检索与安全网关，就能在成本、速度、风控之间取得平衡。本文基于掘金实战教程，拆解一套可直接复用的 Agent 搭建流程，适合运维、IoT、工业 AI 方向的开发者。

📝 一步步教你做

1

第1步：准备双模型 API 与路由策略

在 DeepSeek 平台分别创建 V4.1-Flash 和 V4-Pro 的 API Key，写入环境变量 DEEPSEEK_FLASH_KEY 和 DEEPSEEK_PRO_KEY。定义路由规则：用户问题若命中「急停、困人、异响、门锁」等安全关键词，或意图为故障诊断，则走 V4-Pro；其余日常保养问答走 V4.1-Flash。用 Python 写一个 route_model(query) 函数返回模型名，并记录路由日志便于后续调优。
💡 小贴士：先用小流量灰度，把路由决策日志打到 ELK 或本地文件，观察一周再调整关键词表。
2

第2步：搭建混合检索知识库

收集电梯维保手册、故障代码表、历史工单，切块后分别写入 Chroma 向量库和 BM25 索引。检索时同时跑向量相似度和 BM25 关键词匹配，用 RRF（倒数排名融合）合并结果，取 Top-5 作为上下文。这样既能召回语义相近的案例，又能精准命中「E51 门锁故障」这类代码。
💡 小贴士：切块时保留章节标题作为元数据，检索结果里带上来源页码，方便维保人员核对原文。
3

第3步：实现安全网关与风控拦截

在 Agent 入口加一层安全网关：先做输入过滤（禁止危险操作指令、注入攻击），再对模型输出做规则校验——涉及「短接门锁、屏蔽安全回路」等违规建议直接拦截并转人工。网关同时记录每次调用的模型、耗时、token 消耗，形成审计日志，满足特种设备可追溯要求。
💡 小贴士：把拦截规则做成可配置的 YAML 文件，法规更新时改配置即可，不用改代码。
4

第4步：组装 Agent 主流程

主流程为：接收问题 → 安全网关输入过滤 → route_model 选模型 → 混合检索取上下文 → 拼接提示词模板（角色：电梯维保专家；约束：只基于检索内容回答，不确定时建议转人工）→ 调用对应 DeepSeek 模型 → 输出经安全网关校验 → 返回答案并附来源。用 FastAPI 暴露 /ask 接口，请求体包含 query 和 session_id。
💡 小贴士：提示词里明确要求模型输出 JSON（answer、confidence、sources），方便前端展示和后续自动化处理。
5

第5步：压测与成本对比

准备 100 条真实维保问答，分别用纯 Pro、纯 Flash、双路由跑一遍，对比准确率、平均延迟和 token 成本。预期双路由在准确率接近纯 Pro 的前提下，成本下降 40% 以上、平均延迟下降 50% 左右。根据结果微调路由关键词和检索 Top-K。
💡 小贴士：用 LangSmith 或自建表格记录每次调用的模型与评分，形成可复现的评测集。

✨ 完成后你会得到

完成部署后，访问 /ask 接口提问「电梯门锁反复断开怎么排查」，系统自动路由到 V4-Pro 并返回带来源的排查步骤；提问「电梯多久做一次保养」则走 V4.1-Flash 秒回。安全网关能拦截违规建议，日志中可看到每次调用的模型、耗时与成本。

❓ 常见问题

双路由的关键词表怎么定？ ▼
先从历史工单里统计高频故障词和安全词，形成初版；上线后每周看路由日志，把误判样本补进关键词表或改用小分类模型做意图识别。
混合检索的 RRF 参数怎么调？ ▼
RRF 的 k 值一般取 60，向量和 BM25 各取 Top-20 再融合取 Top-5；如果发现代码类查询召回差，可提高 BM25 权重。
安全网关会不会误拦正常回答？ ▼
规则先设为「命中即转人工」而非直接报错，人工复核后再决定是否放行，同时把误拦样本加入白名单。
没有电梯行业数据能跑通吗？ ▼
可以，先用公开的电梯维保规范和安全技术规范做知识库，跑通流程后再替换为企业私有工单数据。
成本大概能降多少？ ▼
按教程压测数据，日常问答占比约 70% 走 Flash，整体 token 成本可降 40%-60%，具体取决于问题分布。

🚀 进阶玩法

  • 🔹 变体1：把双路由换成「小模型意图分类 + 大模型兜底」，用本地 7B 模型做路由决策，进一步降低路由成本。
  • 🔹 变体2：在安全网关后加一层「人工审核队列」，高风险回答先推给值班工程师确认再返回，适合法规更严的场景。
  • 🔹 变体3：将检索结果与工单系统打通，Agent 回答后自动生成维保工单草稿，形成闭环。
