🎯 为什么值得玩

一年前为业务部门开发的 Hive SQL 离线分析脚本，随着数据量增长从几分钟变成几小时，严重影响报表产出。很多同学遇到慢查询只会加资源，却不知道问题出在 join 倾斜、全表扫描还是 Tez 的 DAG 切分不合理。本玩法通过「看执行计划 → 查表统计信息 → 针对性改写 SQL」三步闭环，帮你定位瓶颈并落地优化，适用于所有基于 Tez 引擎的 Hive 数仓离线任务调优场景。

🧰 你需要准备

  • Apache Hive（含 Tez 引擎） → 访问
    用于执行 SQL 并查看 Tez 执行计划，建议 Hive 2.x 以上
  • Apache Tez → 访问
    Hive 的 DAG 执行引擎，需在 hive-site.xml 中配置 hive.execution.engine=tez
  • Hadoop/YARN 集群 → 访问
    提供底层存储与资源调度，用于查看任务日志和资源使用
  • Hue 或 Hive CLI/Beeline → 访问
    提交 SQL 和查看执行计划的客户端工具

📝 一步步教你做

1

第1步：确认引擎并开启执行计划输出

在 Hive 客户端执行 set hive.execution.engine=tez; 确认当前使用 Tez 引擎。然后对慢脚本加上 EXPLAIN 关键字（或 EXPLAIN EXTENDED）查看逻辑执行计划，重点关注 Stage 依赖关系、Map/Reduce 算子以及是否有 Cartesian Product。也可以执行 EXPLAIN FORMATTED 查看更详细的算子信息。
💡 小贴士：先用 EXPLAIN 而不是直接跑任务，避免浪费集群资源；把执行计划保存到文件方便对比优化前后差异。
2

第2步：分析 Tez DAG 与 Stage 瓶颈

在 Tez UI（通常为 YARN ResourceManager 页面中的 Tez 视图）中打开对应任务的 DAG 图，观察哪个 Vertex 耗时最长、哪个 Edge 发生大量数据 Shuffle。重点看 Map 输入数据量、Reduce 输出数据量以及是否存在数据倾斜（某个 Task 处理量远大于其他）。结合执行计划中的 Stage 划分，判断是扫描阶段慢、Join 阶段慢还是聚合阶段慢。
💡 小贴士：Tez UI 中 Vertex 的颜色和耗时条能快速定位长尾任务；如果某个 Reduce Task 耗时是其他的数倍，基本可判定为数据倾斜。
3

第3步：查看并更新表统计信息

执行 ANALYZE TABLE 表名 COMPUTE STATISTICS 收集表级统计信息，对分区表使用 ANALYZE TABLE 表名 PARTITION(分区字段) COMPUTE STATISTICS。再执行 ANALYZE TABLE 表名 COMPUTE STATISTICS FOR COLUMNS 收集列级统计信息。统计信息准确后，Tez 优化器才能正确选择 Join 顺序、判断是否使用 Map Join，避免生成低效计划。
💡 小贴士：统计信息过期是慢查询的隐形杀手，建议在 ETL 完成后自动触发 ANALYZE，或设置 hive.stats.autogather=true 自动收集。
4

第4步：针对性改写 SQL 脚本

根据前几步定位的瓶颈改写 SQL：小表 Join 大表时使用 /*+ MAPJOIN(小表) */ 提示或调大 hive.auto.convert.join.noconditionaltask.size；数据倾斜时对倾斜 key 加随机前缀打散后再聚合；避免 SELECT * 只取必要列；用分区过滤裁剪数据；将多次重复扫描的 CTE 结果落地临时表。改写后再次 EXPLAIN 对比计划变化。
💡 小贴士：改写要一次只改一个点并对比耗时，避免多个改动混在一起无法判断哪个生效；优先解决最大的瓶颈而不是全面重写。
5

第5步：调优 Tez 参数并验证效果

根据 DAG 分析结果调整 Tez 参数，例如设置 tez.grouping.max-size 控制输入分片大小、hive.tez.container.size 调整容器内存、tez.runtime.io.sort.mb 调整排序缓冲区。调整后重新运行脚本，对比优化前后的执行时间、Shuffle 数据量和 Tez UI 中的 DAG 耗时，确认优化生效并记录参数配置。
💡 小贴士：参数调优要小步快跑，每次只调 1-2 个参数并记录基线；不要盲目调大内存，先确认瓶颈是 CPU、内存还是 IO。

✨ 完成后你会得到

慢脚本执行时间明显下降（常见从小时级降到分钟级），Tez UI 中长尾 Vertex 消失或耗时大幅缩短，Shuffle 数据量减少，执行计划中不再出现全表扫描和不合理的 Cartesian Product，任务稳定可复现。

❓ 常见问题

没有 Tez UI 权限怎么办？ ▼
可以找集群管理员开通 YARN ResourceManager 的 Tez 视图访问权限，或通过 yarn application -list 找到 applicationId 后查看日志中的 DAG 信息。
ANALYZE 统计信息很慢，必须每次都跑吗？ ▼
不必每次全量跑，可只对参与 Join 和聚合的关键表/分区按需收集，或在 ETL 后增量收集，配合 hive.stats.autogather 自动收集基础统计。
MAPJOIN 提示加了但没生效？ ▼
检查小表大小是否超过 hive.auto.convert.join.noconditionaltask.size 阈值，以及是否使用了 LEFT JOIN 等不支持 Map Join 的场景，必要时调大阈值或改写 Join 顺序。
数据倾斜加随机前缀后结果不对？ ▼
加前缀后需要两阶段聚合：先按「前缀+key」聚合，再去掉前缀按原 key 二次聚合，确保最终结果与原来一致。
优化后过一段时间又变慢了？ ▼
数据量增长或统计信息过期都可能导致回退，建议把 ANALYZE 和关键 Tez 参数固化到调度脚本中，并定期复查执行计划。

🚀 进阶玩法

  • 🔹 变体1：把执行计划分析做成自动化脚本，定期对慢 SQL 跑 EXPLAIN 并对比 DAG 耗时，提前发现性能回退。
  • 🔹 变体2：将 Tez 调优经验迁移到 Spark SQL 引擎，对比同一 SQL 在 Tez 与 Spark 下的执行计划和耗时，选择更优引擎。
  • 🔹 变体3：结合 Hive 的 CBO（基于代价优化）开启 hive.cbo.enable=true，配合准确统计信息让优化器自动选择更优 Join 顺序和算法。

💡 一句话总结

用 Tez 执行计划定位瓶颈、用统计信息喂饱优化器、用针对性 SQL 改写和参数调优解决瓶颈，形成「看计划→查统计→改 SQL→调参数→验效果」的慢查询优化闭环。
