🎯 为什么值得玩

MCP 旨在让外部服务按统一协议暴露工具，客户端按统一协议发现并调用，双方无需为彼此写胶水代码。很多开发者觉得协议很神秘，其实核心就是 JSON-RPC 风格的请求/响应。本教程带你从零手写客户端与服务端，打通一个真实的外部工具（如天气查询），看清协议本质，为后续接入更多工具链打下基础。

  • VS Code 或任意编辑器 → 访问

  • curl 或 Postman → 访问

  • 一个可调用的外部 API（如 OpenWeatherMap 免费天气 API） → 访问
    作为被 MCP 暴露的外部工具

📝 一步步教你做

1

第1步：定义 MCP 消息格式与工具描述

先约定客户端与服务端之间的 JSON 消息结构：请求包含 jsonrpc、id、method、params；响应包含 jsonrpc、id、result 或 error。工具描述用 name、description、inputSchema 三个字段，其中 inputSchema 采用 JSON Schema 描述参数。把这份约定写成一个共享的 protocol.py 文件，后续两端都导入它，保证格式一致。
💡 小贴士：不用追求完整规范，先实现 tools/list 和 tools/call 两个方法即可跑通核心流程。
2

第2步：手写 MCP 服务端（暴露外部工具）

用 Python 标准库 http.server 起一个 HTTP 服务，监听 /mcp 路径。收到 POST 请求后解析 JSON，根据 method 分发：tools/list 返回工具列表（包含天气查询工具及其 inputSchema）；tools/call 根据工具名调用真实的外部天气 API，把结果包装成 MCP 响应返回。外部 API 的密钥从环境变量读取，不要硬编码。
💡 小贴士：先用 curl 手动发一条 tools/list 请求，确认服务端能返回正确 JSON，再写客户端。
3

第3步：手写 MCP 客户端（发现并调用工具）

客户端同样用 Python 标准库 urllib 或 requests 向服务端 /mcp 发 POST 请求。先调用 tools/list 拿到工具列表并打印；再根据用户输入构造 tools/call 请求，传入工具名和参数（如城市名），发送后解析响应，提取结果字段展示给用户。把请求 id 用递增整数管理，方便匹配响应。
💡 小贴士：客户端里加一个简单的命令行交互循环，输入城市名就调用一次，体验更直观。
4

第4步：联调与错误处理

启动服务端，再运行客户端，依次测试：正常调用、工具名不存在、参数缺失、外部 API 超时。服务端对未知 method 返回 error 对象，对工具执行异常捕获后返回 error 而不是崩溃。客户端对 error 响应做友好提示。确保两端对 id 的匹配逻辑正确，避免响应错位。
💡 小贴士：在服务端日志里打印收到的原始 JSON，排查协议问题时非常有用。
5

第5步：接入第二个工具，验证协议扩展性

再写一个简单工具，比如“当前时间查询”或“随机名言”，在服务端 tools/list 中追加描述，在 tools/call 中增加分支。客户端无需修改任何代码，就能发现并调用新工具。这直接证明了 MCP 的价值：新增工具只需服务端注册，客户端自动发现。
💡 小贴士：把工具实现拆成独立函数，用字典注册表管理，后续加工具就是加一行注册。

❓ 常见问题

必须用 HTTP 吗？能不能用 stdio？ ▼
MCP 支持多种传输方式，stdio 也很常见。本教程用 HTTP 是为了方便用 curl 调试，你可以把服务端改成从标准输入读 JSON、向标准输出写 JSON，客户端用 subprocess 启动它即可。
inputSchema 必须写完整 JSON Schema 吗？ ▼
建议至少写 type、properties 和 required，这样客户端才能做参数校验和提示。简单工具可以只写 type 和 properties，但完整一点更利于后续接入通用客户端。
外部 API 密钥怎么管理？ ▼
用环境变量读取，不要写进代码或提交到仓库。本地可以建 .env 文件并用 python-dotenv 加载，生产环境用密钥管理服务。
客户端如何知道服务端有哪些工具？ ▼
通过 tools/list 方法动态获取，不要硬编码工具列表。这样服务端新增工具时客户端零改动，这正是 MCP 的设计目标。
手写版和官方 SDK 版有什么区别？ ▼
手写版帮你理解协议本质，但缺少连接管理、重试、流式响应等工程能力。生产环境建议用官方 SDK，手写版适合学习和快速验证。

🚀 进阶玩法

  • 🔹 变体1：把服务端改成 stdio 传输，客户端用 subprocess 启动服务端进程，体验本地工具进程模式。
  • 🔹 变体2：增加 resources/list 和 prompts/list 方法，让服务端除了工具还能暴露静态资源和提示词模板。
  • 🔹 变体3：把客户端接到一个真实 LLM（如 OpenAI API），让模型根据用户问题自动选择工具并生成 tools/call 参数，形成完整 Agent 循环。

MCP 的本质就是一套极薄的 JSON 消息约定，手写一遍客户端与服务端，你就能看清工具发现与调用的全貌，从此接入任何外部工具都不再神秘。
