🎯 为什么值得玩

随着 Agent 处理的任务越来越复杂，上下文窗口容易堆积大量低信号信息，导致模型注意力分散、推理质量下降，这就是“上下文腐烂”。Anthropic 提出的上下文工程法通过筛选高信号信息、压缩上下文、引入 Agentic Memory 和子 Agent 等策略，显著提升 Agent 的稳定性和效率。本教程拆解该方法，并给出可落地的提示词优化步骤，适合正在构建复杂 Agent 的开发者。

📝 一步步教你做

1

第1步：识别上下文腐烂与高信号信息

先分析你的 Agent 当前提示词和对话历史，找出哪些信息是低信号（如重复的确认、无关的闲聊、过时的中间结果），哪些是高信号（如任务目标、关键约束、最新状态）。可以用一个简单表格列出每类信息及其出现频率。然后设定规则：只保留高信号信息，低信号信息要么删除，要么压缩成一句话摘要。
💡 小贴士：可以要求 Claude 帮你标注一段对话中的高信号与低信号句子，快速建立判断标准。
2

第2步：设计上下文压缩策略

针对长对话或长文档，制定压缩规则。例如：每轮对话后，让模型用一句话总结本轮新增的关键信息；对于工具调用结果，只保留结论和关键数据，丢弃原始日志。在提示词中明确写出压缩指令，如“请将以下内容压缩为不超过50字的高信号摘要”。同时设置压缩触发条件，比如上下文超过2000 token 时自动压缩。
💡 小贴士：压缩时保留时间戳和实体名称，避免后续指代不清。
3

第3步：引入 Agentic Memory 管理长期状态

为 Agent 增加一个外部记忆模块，可以用文件、数据库或简单的键值存储。在提示词中定义记忆的读写规则：何时写入记忆（如任务阶段完成、关键决策点），何时读取记忆（如开始新子任务时）。例如，让 Agent 在每完成一个子任务后，将结果摘要写入 memory 文件，并在下一轮开始时先读取该文件。这样上下文窗口只保留当前任务所需的高信号信息。
💡 小贴士：记忆内容也要定期压缩和清理，避免记忆本身膨胀。
4

第4步：使用子 Agent 拆分复杂任务

将复杂任务拆分为多个子任务，每个子任务由一个独立的子 Agent 处理，子 Agent 只接收与自身任务相关的高信号上下文。主 Agent 负责调度和汇总结果。在提示词中定义子 Agent 的职责、输入输出格式以及主 Agent 的协调逻辑。例如，主 Agent 先分解任务，然后依次调用子 Agent，每个子 Agent 返回压缩后的结果，主 Agent 再整合。
💡 小贴士：子 Agent 之间尽量不共享完整上下文，只传递必要的接口信息，减少污染。
5

第5步：用 5 张工单做 token 对比与迭代

准备 5 个有代表性的工单（任务），分别用原始提示词和优化后的提示词运行，记录每次的 token 消耗和任务完成质量。对比分析哪些优化最有效，哪些地方还有冗余。根据结果调整压缩阈值、记忆规则或子 Agent 划分。重复迭代直到 token 消耗和效果达到平衡。
💡 小贴士：工单要覆盖不同复杂度，至少包含一个长上下文任务和一个多步骤任务。

✨ 完成后你会得到

优化后的 Agent 在相同任务上 token 消耗降低 30%-50%，同时任务完成质量和稳定性明显提升，长任务中不再出现上下文腐烂导致的逻辑混乱或遗漏。

❓ 常见问题

上下文压缩会不会丢失重要信息？ ▼
合理设计压缩规则可以保留高信号信息。建议压缩时保留实体、时间、关键决策和约束条件，并定期人工抽查压缩结果。
Agentic Memory 用什么实现最简单？ ▼
初期可以用本地文本文件或 JSON 文件，按任务 ID 存储摘要。生产环境可换用 Redis 或向量数据库。
子 Agent 会增加调用成本吗？ ▼
子 Agent 会增加调用次数，但每个子 Agent 的上下文更短，总体 token 可能反而下降。需要根据任务复杂度权衡。
如何判断上下文是否已经腐烂？ ▼
观察 Agent 是否开始重复之前的信息、忽略最新指令或回答偏离主题。也可以监控上下文长度和 token 利用率。

🚀 进阶玩法

  • 🔹 变体1：将压缩策略改为滑动窗口+摘要，只保留最近 N 轮对话和全局摘要，适合客服对话场景。
  • 🔹 变体2：用向量数据库实现语义记忆检索，Agent 根据当前任务动态检索相关记忆片段，适合知识密集型任务。
  • 🔹 变体3：引入多个子 Agent 并行处理不同子任务，主 Agent 做结果融合，适合可并行拆分的复杂工作流。

💡 一句话总结

上下文工程的核心是持续筛选高信号信息、压缩冗余、外置记忆并拆分任务，让 Agent 在有限上下文窗口内保持高效推理。
