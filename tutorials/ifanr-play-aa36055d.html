📝 一步步教你做

1

第1步：定义评测任务集与评分维度

从你日常真实使用场景中挑选 10-15 个代表性任务，覆盖推理、代码、写作、指令遵循四类。为每个任务写一条固定提示词，并定义 1-5 分的评分标准（如准确性、完整性、格式合规）。把任务清单和评分表建在 Google Sheets 中，确保后续所有模型用完全相同的输入。
💡 小贴士：任务集不要贪多，10 条高质量、有区分度的提示词比 100 条泛泛而问更有用。
2

第2步：编写批量调用脚本

用 Python 写一个脚本，读取任务清单中的提示词，依次调用 GPT-6.2 Astra 和对比模型（如 GPT-5.5）。每次调用固定 temperature=0、max_tokens 一致，并把模型名、提示词、输出、耗时写入 CSV。建议加一个 sleep 避免触发速率限制。
💡 小贴士：用环境变量存 API Key，不要把密钥硬编码进脚本；对同一提示词可跑 2-3 次取平均，降低随机性干扰。
3

第3步：人工盲评与打分

把 CSV 中的模型输出复制到评分表中，隐藏模型名称（盲评），逐条按第1步的评分维度打分。至少找一位同事交叉评分，减少个人偏好。重点记录模型“翻车”的具体表现，比如格式错误、事实错误、拒绝回答等。
💡 小贴士：盲评是关键——知道模型名字后，人很容易产生“贵的就是好”的偏见。
4

第4步：汇总对比与归因分析

计算每个模型在各维度上的平均分和总分，画出简单的柱状图或雷达图。对分差较大的任务，回看原始输出，判断是模型能力差异还是提示词歧义导致。结合爱范儿文章中的观点，区分“聪明”（推理深度）和“好用”（指令遵循、格式稳定）两个维度分别打分。
💡 小贴士：不要只看总分——某个模型可能总分低但在你的核心场景上表现更好，按场景加权更合理。
5

第5步：形成结论并复测

根据对比结果写出结论：GPT-6.2 Astra 在你的任务集上是否被冤枉？它在哪些任务上强、哪些弱？如果结论与社区口碑差异大，换一批提示词或调整 temperature 后复测一次，确认结论稳健。最后把评测脚本和评分表存档，方便下次新模型发布时直接复用。
💡 小贴士：把评测集当成长期资产维护，每次新模型发布只需替换模型名重跑，效率极高。

❓ 常见问题

没有多个模型的 API 权限怎么办？ ▼
可以只评测 GPT-6.2 Astra 与一个你常用的旧模型，甚至用网页版手动复制输出到表格中，流程完全一样，只是自动化程度低一些。
评测任务集应该选多少条？ ▼
建议 10-15 条，覆盖 3-4 类场景即可。太少没有统计意义，太多人工评分成本过高，容易半途而废。
人工评分太主观怎么办？ ▼
把评分维度拆细（如准确性、完整性、格式合规各 1-5 分），并找第二个人独立盲评，取平均分；对分歧大的条目回看原始输出讨论定分。
temperature 设多少合适？ ▼
评测对比建议统一设为 0 或接近 0，减少随机性；如果你关心创意类任务，可单独设一组 temperature=0.7 的对照实验。
这个流程能用于非 GPT 模型吗？ ▼
完全可以。只要模型提供 API 或网页版，把调用方式替换掉即可，评分表和对比逻辑通用。

🚀 进阶玩法

  • 🔹 变体1：A/B 盲测投票——把两个模型的输出匿名并列展示给同事，让大家投票选更好的，最后揭晓模型名，适合快速感知“好用度”。
  • 🔹 变体2：成本-性能二维对比——在评分基础上记录每个模型的 token 成本和响应延迟，画出性价比散点图，适合团队做 API 选型决策。
  • 🔹 变体3：回归测试集——把历史评测中模型翻车的提示词单独整理成“回归集”，每次新模型发布先跑这一组，快速判断旧问题是否修复。
